# Auris Oculi 感知工具箱

> 一个全本地的音视频分析插件，跑在 DeepSeek Harness 上。
> 不联网、不上传、不依赖云服务。

---

## 它解决什么问题

给一段音频，人耳朵能听出很多东西：说话的人是不是同一个人、语速急不急、
声音抖不抖、有没有背景噪声。但这些**感觉**没法量化，也就没法比较、没法复核。

这个插件把这些感觉变成数字：

```
基频中位 152 Hz   音域 11.3 半音   微颤 0.38
音量起伏 3.2 dB   语速 3.3 字/秒   谐噪比 4.9
```

27 个数字，每一个都能复现、能对比、能被别人验证。

## 五个能实际用上的场景

### 一、判断两段录音是不是同一个人

```ts
speaker_compare({ a: "录音1.wav", b: "录音2.wav" })
```

几秒返回结果。实测在同一支录音、同一环境下，同人相似度 0.82~0.89，
异人 −0.01，**中间是空的，没有灰色地带**。

**关键前提**：给 4 秒以上音频。同一段录音切两半算同人相似度：

| 每段时长 | 相似度 |
|---|---|
| 1 秒 | 0.58 |
| 2 秒 | 0.56 |
| 4 秒 | 0.71 |
| **8 秒** | **0.88** |

8 秒是拐点。太短的音频会给出偏低的分数，`caveats` 里会提示。

### 二、一条视频，画面和声音一起看

```ts
toolbox_analyze({ source: "video.mp4" })
```

画面走「抽帧 → 拼图 → 本机视觉模型」，声音走「韵律 + 转写」，两条流水线并行。

适合：会议录像、教学视频、需要核对画面上文字的场景。
**注意**：视觉模型对中文画面的 OCR 不完美，关键帧建议人工核对。

### 三、描述一段声音，而不是评价它

```ts
prosody_analyze({ source: "会议录音.mp3" })
```

返回 27 个数字，分四组：

| 组 | 测什么 | 例子 |
|---|---|---|
| 韵律 | 音高、音域、微颤、清浊、响度 | 基频 152 Hz，音域 11 半音 |
| 频谱 | 音色亮度、高频边界、噪声性、沙哑度 | 质心 2543 Hz，谐噪比 4.9 |
| 音强包络 | 音量起伏的快慢和幅度 | 音量起伏 3.2 dB |
| 语速 | 每秒字速、说话占比 | 3.3 字/秒，4 句，均 8 秒 |

**这些数字能描述声音，但不能判断情绪。** 原因见下面「诚实的边界」。

### 四、一段录音里有几个人

```ts
speaker_diarize({ source: "会议.mp4" })
```

按 2 秒窗算嵌入、聚类、合并成段，返回「谁在第几秒说话」。

**这个功能不可靠，必须看 `caveats`。** 实测真实 2 人对话会被判成 1 人，
单人录音会被判成 2 人。返回里会明确说「这可能是分不出来，而不是真的只有一个人」。

### 五、判断一批标注值不值得用

```ts
toolbox_benchmark({ dir: "D:/我的样本" })
```

给一个带标签的文件夹，它跑三个任务（分标签、判同标签、距离间隔），
对比三档特征（韵律 / MFCC / 说话人嵌入），每项都给随机基线。

**这个工具的价值不是提取数字，是判断数字能不能支撑结论。**
它回答「我这批录音够不够用」「这几个标签到底能不能分开」。

## 三个真实例子

### 例子 1：分不清两个相似的声音

用 CASIA 语料里两个不同的人，各取一条。Resemblyzer 给 0.5179（看着像同一人），
CAM++ 给 **0.1248**（明显不是）。

差别在于「异人基准」：Resemblyzer 把不同人也拉到 0.52，
因为它把所有声音挤在同一个锥角里（各向异性）。CAM++ 压到 0.26。

**所以插件支持两个模型后端**，配置 `speaker.backend` 选更准的那个。

### 例子 2：打哈欠被当成说话

一段打哈欠的录音，基频 132 Hz、浊音 68% —— 看着就是「正常说话」。

但它的音域是 **23.1 半音**，而正常说话是 8~15。插件据此判为
「是人声，但不是说话」，不会把它混进语气分析里。

实测 15 类非言语声音（打哈欠、磨牙、牙齿打颤、弹舌、清嗓…），
**76.1% 能正确识别**。机械音接近 100%，哭和尖叫只有 25% / 17%——
它们和说话共用发声机制，抓不住。

### 例子 3：情绪分类到底能不能做

这是最有意思的一个。同一个任务，三种做法的结果：

| 做法 | 准确率 | 随机基线 |
|---|---|---|
| 让 LLM 判断「这是什么情绪」 | 13.9% | 16.7% |
| 9 维韵律特征 + 最近邻 | **40.4%** | 16.7% |
| 62 维声学特征 + 最近邻 | **81.3%** | 22.8% |

**结论**：不是情绪分不开，是**不该让 LLM 用语言去判断**。

但换成**真实说话**（有内容的句子，不是「啊——」这种发声），只有 34.3%，随机 14.3%。

区别在于：非言语发声的情绪在声学上极其显著，真实说话则被语言内容淹没。

## 诚实的边界

这个插件有三件事做不到，而且**不打算假装能做到**。

### 一、它不判断情绪

27 个数字都是可验证的，但「这段是什么情绪」做不到。

真实说话 7 类情绪分类只有 **34.3%**（随机 14.3%）。
决定性指标不是准确率，是「边际/散布」比值——它始终在 0.06~0.08，
意味着各类在特征空间里**挤在一起**，最近邻的选择由噪声决定。

所以它能做「测量」，不能做「判断」。

### 二、聚类和分离不可靠

这两个工具都基于 Resemblyzer 嵌入，而它在这类音频上区分力不足：
同人内部 0.79、不同人之间 0.75，**只差 0.04**。

根因不是聚类算法，是嵌入本身没有区分度。所以返回里会带可信度信号，
不可信时说清「这可能是分不出来」。

### 三、还没验证跨设备

声纹比对目前只在「同一支录音、同一环境」上验证过。
**换麦克风、换嘈杂环境还没验**——这是最可能在实际使用中出问题的地方。

## 技术选择

### 为什么不用 LLM 做数值判断

试过了。qwen3.5:4b 对情绪的判定，三次实验都是 13.9%（随机 16.7%），
置换检验显示三次输出的**相似度 100% 相同**——模型根本没在看输入。

它擅长的是给数字排序（153→233 Hz 排序 100% 正确）、读数值大小。
不擅长的是「韵律 → 语义」这层映射。

**结论：数值计算交给算法，语义判断不交给小模型。**

### 为什么支持两个说话人模型

| 后端 | 维度 | 异人基准 | 错误率 | 安装 |
|---|---|---|---|---|
| `resemblyzer` | 256 | 0.52 | 19.5% | pip 装即可 |
| `campplus` | 192 | **0.26** | **6.4%** | 需 27 MB 模型 |

CAM++ 的价值不在「同人更像」，而在**异人基准低**——判断「不像」时可靠得多。

但 CAM++ 需要单独下模型，所以做成可选：默认 `auto`（有就用），
没装的机器行为完全不变。

**⚠️ 两个后端的余弦坐标系完全不同，阈值必须分开。**
拿 Resemblyzer 时代的 0.70 去看 CAM++ 的数字，会把所有同人判成「不像」。

### 为什么用表驱动的清理规则

8 个任务目录，每个的「保留什么、删什么」都不同。写成表之后：

```js
prosody: {
  keep: [/^prosody\.(json|md)$/, /^job\.(json|log)$/],
  drop: [/^decoded\.wav$/, /^source\./, /^_cmp$/]
}
```

规则来源于**读 python 源码确认的实际输出文件名**，不是猜的。
改 python 的写盘名字必须同步改这张表。

## 规模

| 项 | 数字 |
|---|---|
| 工具 | 12 个 |
| HTTP 路由 | 44 条 |
| 配置项 | 41 个（每个都有明确通路） |
| 代码 | `index.js` 6544 行 + 9 个 Python 脚本 |
| 自动化测试 | 4 套（64 条 Host 断言 + 冒烟 + 配置审计 + 分类回归） |

**代码结构**：

```text
index.js      Host 半：工具注册、路由、配置、任务调度
client.js     浏览器半：手写，无构建步骤，无 JSX
prosody.py    韵律 + 频谱 + 包络 + 语速 + 转写 + 多后端嵌入
video_watch.py 抽帧 + 拼图 + 视觉模型
speaker_*.py  比对 / 聚类 / 分离
```

**没有构建步骤**——`client.js` 是手写的，用 `h()` 而不是 JSX，
改完刷新就生效。这省掉了一整套工具链。

## 装和用

DSH → **Plugins → Add plugin** → 选这个目录。

依赖分三档：
必装（librosa 那一套）、按功能（转写 / 声纹）、可选（更强模型）。

完整的依赖清单和已知陷阱在 [安装指南](INSTALL.md)。两个最容易卡住的：

- `webrtcvad` 在 Python 3.12 上编译失败，必须用 `webrtcvad-wheels`
- `resemblyzer` 首次运行会下载 200 MB 的 encoder，看起来像卡住

## 设计上的一个取舍

**回执默认不带曲线数据。**

逐帧曲线是 0.01 秒一帧，一分钟音频就是 3 MB JSON。
对读回执的模型来说，这 3 MB 几乎全是噪音。

所以默认只给汇总数字，需要时用 `includeCurves: true` + `curveStep` 降采样。

类似的取舍还有几处，都写在代码注释里——包括为什么这么做、试过什么、
什么情况下会失效。

## 数据

`labels/labels.json` 是唯一不可再生的数据（手工标注的样本）。
任何清理逻辑都跳过了它，测试里也有断言检查这一点。

其他所有东西（解码的 wav、抽出的帧、下载的源视频）都可以随时清掉重建。
